# Archiver code audit — 2026-09-11

Scope: `backend/`, `frontend/`, `worker-common/`, `embed-worker/`, `scraper-*/`, `deploy/`, `Jenkinsfile`, `web/`, DB schema V1–V8. Every backend Java file was read once; every frontend route; worker-common and embed-worker in full; scrapers by checksum/diff plus two `main.py` in full. The live Portainer stack file (#183) and running containers were compared against `deploy/docker-compose.yml` (identical, `EXIT=0`).

Items fixed in the last 48 hours (the list in the brief) are excluded.

Severity: **CRITICAL** = data loss, double billing, or silently wrong results in production today. **HIGH** = a real bug or a blocker for Part 2. **MEDIUM** = maintainability debt with a concrete failure mode. **LOW** = hygiene. Effort: S ≤ half a day, M ≤ 3 days, L > 3 days.

## What is good — do not touch

- **`BatchOrchestrator` + `ProviderBatchRepository` + `JobRepository.claimBatch`** (`service/BatchOrchestrator.java`, `repository/JobRepository.java:45-116`). The four-phase design, the `custom_id = job.id` decision, `SUBMIT_GRACE`, `isStillClaimedBy` guarding re-reads, `failRemaining` before `markCollected`, the byte-sized claim with the "first row always qualifies" rule. This is the best code in the repo. Part 2 wraps it; it does not rewrite it.

- **`PipelineGateService`** and the fact that both claim paths go through it (`JobService.java:78-111`).
- **`MarkdownPdfRenderer` / `CoverSheetService`**: focused, tested, no shared mutable state.
- **`ProcessorTokenFilter`** constant-time compare, **`ProxyAuthFilter`** remote-addr trust, **`TrustedPeerResolver`** — all tested.
- **`worker_common.markdown`** — one implementation, tested, used by every Python worker.
- **`MarkdownText.svelte`** — sanitised `{@html}`, image-ref rewriting, correct.
- Test suites `PipelineAuditTest`, `PipelineStateMachineTest`, `TranslationServiceTest`, `PdfExportServiceTest` are load-bearing and thorough.

## 1.2 Findings in detail

### C1 — Batch machinery is untested
`BatchOrchestrator` is the component the brief calls "battle-tested". It is tested by production only. Nothing exercises: reconcile adopting an orphan via `findByTag`; the 2-minute grace releasing a never-submitted batch with `restoreAttempt=true`; `collectOne` failing the whole file on an unparseable `custom_id`; `failRemaining` before `markCollected`; `applyOne` skipping a job no longer claimed by this batch; the byte budget in `writeRequests` releasing overflow; `pagesSubmittedInLastMinute` budgeting.

**Fix.** Before any Part 2 work: `BatchOrchestratorTest` (Testcontainers, real `JobService`) against a `FakeBatchTransport` (in-memory, scriptable failures) — see §2.9 for the case list — plus `MistralBatchClientTest` with WireMock (already on the test classpath, used by `SemanticSearchTest`). Commit the tests before touching the code.

### C2 — Embedding provider drift
Verified facts: `deploy/docker-compose.yml` is byte-identical to the live stack file; `archiver-embed-tei-1` (`text-embeddings-inference:86-1.9`, `--model-id BAAI/bge-m3`, `runtime: nvidia`) is running; backend and embed-worker both receive the literal `EMBED_TEI_URL: http://embed-tei:80` (`:103`, `:164`), not `${EMBED_TEI_URL}`. Portainer's `EMBED_TEI_URL=https://api.deepinfra.com/v1/openai`, `EMBED_MODEL=Qwen/Qwen3-Embedding-8B`, `EMBED_DIMENSIONS=1024` therefore reach nothing. CLAUDE.md's Embedding section, the "no GPU" claim, and the `embed_worker/main.py:3-5` docstring describe a deployment that does not exist. The 1024-dim halfvec column happens to fit bge-m3, which is why nothing broke.

**Fix.** Decide which is true, then make the compose reference `${EMBED_TEI_URL}`, `${EMBED_MODEL}`, `${EMBED_DIMENSIONS}` in both services and either delete `embed-tei` + `tei_model_cache` or rewrite CLAUDE.md and drop `EMBED_QUERY_PREFIX` (bge-m3 takes no instruction). Then run the known-answer retrieval check CLAUDE.md prescribes. Switching provider means re-embedding 128k pages' chunks (`reset-embeddings`, H1) — a deliberate act, not a side effect of fixing config.

### C3 — `findByStatus` ignores the kind
```java
@Query("SELECT * FROM provider_batch WHERE status = :status ORDER BY id")
List<ProviderBatch> findByStatus(@Param("status") String status, @Param("jobKind") String jobKind);
```
Add `AND job_kind = :jobKind`. Add a test that two stages' `submitting` rows are not visible to each other. This must land before any second provider.

### H1 — Archive-wide delete behind the worker token
Move `resetEmbeddings` to `AdminPipelineController` under `/api/admin/…` (ROLE_ADMIN), require `{"confirm":"text_chunk"}` in the body, log the caller. It also loops one `UPDATE` per record; make it one statement.

### H2 — Dead and unsafe processor endpoints
No worker or scraper references these (grep across all Python and TS):
- `POST /records/{id}/translation` (`:351-366`) — bypasses ranking. **Delete.**
- `POST /pages/{id}/translation` (`:339-349`) — ranked correctly, but no caller. Delete or keep as the sequential hand-off for Part 2.
- `POST /records/{id}/searchable-pdf` (`:243-267`) — for the retired Python pdf-worker; inserts a new attachment row each call (the orphaning `SearchablePdfWorker` fixed). **Delete.**
- `POST /ocr/{id}/artifact` (`:210-237`) — no caller. Delete.
- `POST /entities/{id}` (`:273-298`) — entity-worker is an empty shell. Delete or leave with a comment.
- `POST /audit-pipeline` (`:440-446`) — duplicates `/api/admin/audit` and omits `recoverStaleClaims`. Delete.
`GET /records/{id}/pages` (`:304-326`) **is live** (embed-worker) — keep, drop the confidence ordering.

### H3 — Re-OCR footgun
Replace the literal with `defaultOcrEngine`, refuse when no worker is registered for that kind (`JobEventService.getWorkerCounts()` for external, or the registry from Part 2 for internal), and do not `resetForOcr` a record unless the enqueue is going to succeed. Given the user's standing instruction never to run bulk re-OCR, the `limit=1000` default should become `1`.

### H4 — Reset ignores translation quality
Extract `TranslationEnqueuer.enqueueForRecord(recordId)` from `PipelineStateMachine.enqueuePostOcrJobs` (`:503-537`) and call it from `resetRecordToStage`. Same for OCR enqueue (`PipelineStateMachine.enqueueOcrJobs` vs `JobService:366-372, 785-794`).

### H5 — Default engine points at a disabled worker
Set the default to `ocr_page_mistral` in all four places, or better: one `@ConfigurationProperties` bean and a startup check that fails fast when `default-engine` has no registered internal worker and no external worker kind. Part 2 §2.5 makes this a route.

### H6 — Audit duplicates the state machine
Pass 7 at `JobService:604-612` enqueues `embed_record`; `PipelineStateMachine:316-323` explicitly does not, with a comment explaining the double-embed. Fix: every pass that changes `record.status` should call `stateMachine.autoAdvance(recordId)` and stop writing status itself. Passes 3b, 3c, 4b, 6, 7 collapse into "find records whose guards are satisfied but who never got a `completeJob` nudge → `autoAdvance`". Make each pass its own `@Transactional(REQUIRES_NEW)` method so one failure does not roll back the others (the code already does this for pass 1 and explains why).

### H7 — Startup steals a job
`loop.wait_for_backend` calls `client.claim_job(job_kind)`. If a job is pending it is claimed and dropped. Replace the body with `worker_common.http.wait_for_backend(client.base_url)` (health endpoint) and delete the duplicate. Both are exported from `__init__.py` under confusingly similar names.

# Part 2 — Pluggable AI provider layer

## 2.1 Goals and non-goals

Goals: swap OCR, translation and embedding providers per capability and per mode from the admin UI; keep `BatchOrchestrator`'s guarantees byte-for-byte; make Mistral the first adapter as a pure refactor; never re-run the 128,484 pages; never let a worse translation overwrite a better one.

Non-goals for the first pass: provider-side cost optimisation, multi-region, streaming. The two AI call sites outside the backend (search answer synthesis in SvelteKit, gpt-4o-mini rerank in `PersonMatchService`) are noted as a fourth capability (`COMPLETION`) and folded in at increment 8, not before.

## 2.2 The seam

Today one interface (`BatchStage`) mixes three concerns: *pipeline glue* (which job kind, what to read/write in the DB, `resolveLocally`), *provider request shape* (`buildRequestBody` emits Mistral JSON, `endpoint()` is a Mistral path, `applyResult` parses Mistral's `choices[0].message.content`), and *batch transport* (`MistralBatchClient`, plus the two places `BatchOrchestrator` itself parses Mistral output: `poll()` at `:242-244` reads `succeeded_requests/failed_requests/output_file`; `applyOne` at `:298,311` reads `response.status_code/body`).

Split along those three lines:

```java
package place.icomb.archiver.ai;

public enum Capability { OCR, TRANSLATION, EMBEDDING }
public enum Mode { BATCH, SEQUENTIAL }

/** One configured provider instance ("mistral", "deepinfra-qwen", "ollama-studio"). */
public interface AiProvider {
  String id();
  String displayName();
  Set<Capability> capabilities();
  Set<Mode> modes(Capability c);
  Optional<BatchTransport> batchTransport();       // present iff any capability has BATCH
  Optional<OcrEngine> ocr();
  Optional<Translator> translator();
  Optional<Embedder> embedder();
  ProviderHealth health();                          // last probe, cached
}
```

### Capability interfaces — sequential and batch in one object

Each capability object knows how to make **one request** in either mode. That is deliberate: the batch body and the sequential body are the same JSON for every provider seen so far (Mistral, OpenAI, DeepInfra), and keeping them together stops the two drifting.

```java
public interface OcrEngine {
  String engineId();                 // stored in page_text.engine, e.g. "mistral-ocr"
  String model();
  String contentType();              // OcrContentType.MARKDOWN | PLAIN
  // sequential
  OcrResult ocr(OcrRequest req) throws ProviderException;
  // batch: one JSONL line body and its inverse
  Map<String, Object> batchRequestBody(OcrRequest req);
  OcrResult parseBatchResponse(JsonNode body);
  String batchEndpoint();            // provider routing key, e.g. "/v1/ocr"; null if no batch
}

public record OcrRequest(long pageId, Path image, String langHint) {}
public record OcrResult(String text, String contentType, JsonNode rawResponse) {}

public interface Translator {
  String modelId();                  // stored in page_translation.model — must have a rank (§2.6)
  TranslationResult translate(TranslationRequest req) throws ProviderException;
  Map<String, Object> batchRequestBody(TranslationRequest req);
  TranslationResult parseBatchResponse(JsonNode body);
  String batchEndpoint();
}
public record TranslationRequest(String text, String sourceLang, String targetLang, Kind kind) { enum Kind { PAGE, RECORD_METADATA } }
public record TranslationResult(String text /* or JSON for metadata */) {}

public interface Embedder {
  String modelId(); int dimensions(); String queryPrefix(); String passagePrefix();
  float[][] embed(List<String> texts, boolean isQuery) throws ProviderException;
  // batch optional: default empty, most embedding APIs have none worth using
  default Optional<Map<String,Object>> batchRequestBody(List<String> texts) { return Optional.empty(); }
}
```

### Batch transport — the provider's batch API, and nothing else

```java
public interface BatchTransport {
  String providerId();
  BatchLimits limits();                                     // maxBytes, maxRows, itemsPerMinute, timeout
  String uploadInput(Path jsonl) throws ProviderException;
  String createBatch(String inputFileId, String model, String endpoint, long ourBatchId) throws ProviderException;
  Optional<BatchStatus> poll(String providerJobId);        // empty = could not read; leave as is
  InputStream downloadOutput(String outputRef) throws ProviderException;
  Optional<String> findByTag(long ourBatchId);
  BatchLine parseOutputLine(String jsonl);                  // normalises {custom_id, status, body}
}
public record BatchStatus(State state, int succeeded, int failed, String outputRef) { enum State { RUNNING, DONE, FAILED } }
public record BatchLine(String customId, int httpStatus, JsonNode body) {}
```

`MistralBatchClient` becomes `MistralBatchTransport implements BatchTransport`; the two Mistral-shape parses move out of `BatchOrchestrator` into `poll`/`parseOutputLine`. **That is the entire change to the orchestrator: two field-name parses replaced by two interface calls, and the constructor type changed from `MistralBatchClient` to `BatchTransport`.** Everything else in `BatchOrchestrator` is untouched.

### Stages become capability-generic

```java
public final class OcrStage implements BatchStage {
  OcrStage(String jobKind, Supplier<OcrEngine> engine, PageImages images, PageTextRepository texts, JobService jobs) {...}
  public Map<String,Object> buildRequestBody(Job job) { return engine.get().batchRequestBody(new OcrRequest(...)); }
  public void applyResult(Job job, JsonNode body) {
    OcrResult r = engine.get().parseBatchResponse(body);
    texts.deleteByPageId(job.getPageId());
    texts.insertOcrResult(job.getPageId(), engine.get().engineId(), r.text(), r.contentType(), r.rawResponse().toString());
  }
}
```
`TranslateStage` likewise wraps `Translator` and keeps `unwrapCodeFence`/`stripPreamble` (those are pipeline-side hygiene, not provider-side). `RecordTranslateStage` wraps `Translator` with `Kind.RECORD_METADATA`. `resolveLocally` stays in the stages. The `Supplier<…>` is how routing changes take effect without a restart (§2.5).

### Sequential callers

- `TranslationController.translate` → `routing.translator(SEQUENTIAL).translate(req)`.
- `SemanticSearchController.embedText` → `routing.embedder(SEQUENTIAL).embed(List.of(q), true)`; the embed-worker calls a new `POST /api/processor/embed` that does the same with `isQuery=false`, so passage and query prefixes come from **one** `Embedder` object and the drift trap is closed structurally. (The worker keeps chunking; only the HTTP call moves.)
- `QwenOcrWorker` becomes `OpenAiCompatibleVisionOcrEngine` (sequential only) and the `GenericWorker`-based OCR path is retired in favour of the sequential transport below.

## 2.3 Mistral adapter — a faithful refactor

`MistralProvider implements AiProvider` composed of `MistralBatchTransport` (today's `MistralBatchClient` verbatim plus the two moved parses), `MistralOcrEngine` (body from `OcrBatchStage.buildRequestBody:58-67`, parse from `OcrBatchStage.extractText`), `MistralTranslator` (bodies from `TranslateBatchStage:76-88` and `RecordTranslateBatchStage:89-114`, parse `choices[0].message.content`; sequential `translate` is `TranslationController:125-155`). Mistral has no embedding model in use, so `embedder()` is empty; the current embedding endpoint becomes `OpenAiCompatibleProvider("embedding")` pointing at whatever C2 decides.

Faithfulness checks: the JSONL bodies produced for a fixed job must be byte-identical before and after (golden-file test); `engineId()` must return exactly `"mistral-ocr"`; `Translator.modelId()` must return `mistral-small-latest` / `mistral-medium-latest` so `page_translation` rows keep matching `TranslationModels` ranks; `BatchTransport.limits()` returns today's numbers.

## 2.4 Batch where the provider is sequential-only, and the reverse

**Sequential-only provider in a batch slot** (e.g. Ollama on the Mac Studio, DeepInfra vision): `SequentialBatchTransport implements BatchTransport` wraps a sequential capability so the **orchestrator runs unchanged**:

- `uploadInput(jsonl)` copies the file under `${archiver.storage.root}/batches/{ourBatchId}.in.jsonl`, returns that path as the "file id".
- `createBatch(...)` inserts nothing new — `provider_batch` already exists — and starts a bounded executor (`limits().concurrency`, default 1 for Ollama, 4–8 for hosted APIs) that reads lines, calls `engine.ocr()` / `translator.translate()`, and **appends one output line per completed item** to `{id}.out.jsonl` (`{"custom_id":…, "response":{"status_code":200,"body":…}}`), flushing per line. Returns `"local:"+ourBatchId`.
- `poll` counts completed/failed lines in the `.out` file and reports `DONE` when every input `custom_id` has an output line (or the executor has finished).
- `downloadOutput` streams the `.out` file; `findByTag` checks whether `{id}.in.jsonl` exists — an orphaned local batch is "adopted" by restarting its executor, skipping `custom_id`s already present in `.out`.
- Rate limiting is enforced where it is today (`pagesSubmittedInLastMinute`) plus per-call pacing inside the executor.

Restart safety comes for free: `provider_batch` rows survive, `reconcile()` finds `submitted` local batches with no live executor (an in-memory registry keyed by batch id), and resumes them. Per-line appends make resume idempotent; `isStillClaimedBy` makes re-reading harmless exactly as for Mistral. The `PROVIDER_TIMEOUT` of 24 h still applies.

**Batch-only provider in a sequential slot**: not bridged. A sequential call that has to wait for a batch API is a broken UX for the translate box and a broken query path for search. `AiProvider.modes()` says `BATCH` only, the admin UI refuses to route `(TRANSLATION, SEQUENTIAL)` to it, and `routing.translator(SEQUENTIAL)` throws `ModeNotSupportedException` → 503 "Translation not configured" (the same path `TranslationController:106-108` takes today when the key is missing). If someone really wants "sequential via batch of one", it is a `BatchOfOneTranslator` adapter written later, with an explicit timeout, never the default.

### Credentials: DB vs env — the tradeoff, stated
Storing API keys in `ai_provider` makes the admin UI self-contained but puts live secrets into a database that is backed up, dumped for baselines (`V1__baseline.sql` was generated from a `pg_dump`), reachable by the Portainer stack env credentials, and readable by anyone with `ROLE_ADMIN` in the UI. Encrypting the column with a key from env (`ARCHIVER_SECRETS_KEY`) fixes backups but not the "any admin can read it" problem, and adds a key-rotation story nobody asked for.

**Recommendation:** credentials stay in env (Portainer stack env, as today); `ai_provider.credential_ref` names the env var. The admin UI can add a provider and pick which env var it uses, and shows "credential present / missing" without ever showing the value. Adding a *new* secret is a Portainer env edit + redeploy — one step, rare. Revisit only if a non-technical operator needs to rotate keys without Portainer access. Everything **else** (model names, limits, routing, enabled flags, prefixes) lives in the DB and is editable live.

### Precedence and bad config
1. DB row wins for everything except the secret value.
2. On first boot with an empty `ai_provider` table, seed from the existing `archiver.*` properties (so nothing changes on the migration deploy).
3. Env override for emergencies: `ARCHIVER_AI_ROUTE_<CAPABILITY>_<MODE>=<provider>:<model>` beats the DB and is shown as a banner ("routing pinned by environment").
4. Missing credential, unreachable base URL, unknown adapter `kind`, or a route pointing at a disabled provider → the provider is `UNHEALTHY(reason)`; the affected **routes are marked unavailable and the corresponding job kinds are gated** via `PipelineGateService.set(kind, true, "provider mistral unhealthy: …", "system")`. Jobs queue; nothing is failed; nothing is billed elsewhere. The dashboard already renders held stages. **Never** auto-fall-back to another provider — that is a spend decision.
5. The app never refuses to start because of AI config. It starts, shows what is wrong, and holds work.

### Admin API and UI
`GET /api/admin/ai/providers`, `PUT /api/admin/ai/providers/{id}` (kind, base_url, credential_ref, settings, enabled), `POST /api/admin/ai/providers/{id}/probe` (calls the cheapest sequential method with a 20-token input and reports latency/status — costs a fraction of a cent, logged), `GET/PUT /api/admin/ai/routes` (one row per (capability, mode, job_kind)), `GET /api/admin/ai/status` (health per provider, in-flight batches per provider from `provider_batch`, gated kinds). Frontend: `/admin/ai` tab in the existing admin layout — a provider list with health dots, a routing matrix (rows = capability × mode × kind, cell = provider/model select constrained by `modes()`), and per-provider settings form. The pipeline page's "model actually serving this stage" line starts reading routes instead of worker headers for the internal stages.

### Model choice per route needs a rank
A `(TRANSLATION, *, *)` route's model **must** exist in `translation_model_rank` (§2.6); the UI offers a rank field when the model is new and refuses to save without it. That is what keeps the "never overwrite better" guarantee when a provider is added.

## 2.6 Provider-aware model ranking

`TranslationModels` today: a hard-coded `List.of(UPGRADE_MODEL, BULK_MODEL, LEGACY)` and `jobKindFor(quality)`/`modelFor(quality)`. Replace with a table and keep the semantics.

```sql
CREATE TABLE translation_model_rank (
  model       TEXT PRIMARY KEY,          -- the string stored in page_translation.model
  provider_id TEXT,                      -- informational
  rank        INTEGER NOT NULL,          -- lower is better; unique not required
  note        TEXT
);
INSERT INTO translation_model_rank VALUES
 ('source-en',              NULL,        0, 'original text already English'),
 ('mistral-medium-latest', 'mistral',   10, 'upgrade model; lost no dates/refs on 20-page sample'),
 ('mistral-small-latest',  'mistral',   20, 'bulk model'),
 ('google/gemma-4-31B-it', 'deepinfra', 80, 'record metadata history; mistranslated titles'),
 ('legacy',                 NULL,       90, 'pre-V5 translations from replaced OCR');
```
Unknown models rank 999, as today. `TranslationService`'s eight queries become joins against a view:
```sql
CREATE VIEW page_best_translation AS
SELECT DISTINCT ON (tr.page_id) tr.page_id, tr.model, tr.text_en
FROM page_translation tr LEFT JOIN translation_model_rank r ON r.model = tr.model
WHERE tr.text_en <> ''
ORDER BY tr.page_id, COALESCE(r.rank, 999), tr.created_at DESC;
```
`TranslationModels` keeps its static API for callers (`rank`, `outranks`, `bestFirst`) backed by a cached read of the table (refresh on admin write). `jobKindFor(quality)` stays a pipeline concept: `bulk → translate_page`, `best → translate_page_upgrade`; which **model** each kind uses comes from `ai_capability_route`. The upgrade endpoint (`ViewerController:888-934`) asks the route for the upgrade kind's model and uses `pagesMissingModel(recordId, thatModel)` exactly as now.

Invariant enforced in one place: `TranslationService.refreshShown` recomputes from the view, so whatever model any provider writes, the shown text is the best-ranked, and an admin lowering a model's rank is applied by `refreshAllStale()` (already exists) — no page is ever re-translated to fix ranking. `TranslationServiceTest` already covers the ordering semantics; it needs one new case: "a model added to the rank table after its rows exist takes over on refresh".

## 2.7 `WorkerSchedulingConfig` stops being a wiring god-object

Today: one class, 24 `@Value`s, `new`s every worker and orchestrator, decides the thread pool size, and knows every stage. After:

- `ArchiverAiProperties` — `@ConfigurationProperties("archiver.ai")`, typed, validated; used only for first-boot seeding and the emergency override.
- `ProviderRegistry` (`@Service`) — loads `ai_provider` rows, instantiates adapters via `Map<String, AiProviderFactory>` keyed by `kind` (`mistral`, `openai-compatible`, `ollama`), caches, exposes `Optional<AiProvider> get(id)`, `probe(id)`, and a `reload()` the admin controller calls after a write.
- `CapabilityRouting` (`@Service`) — reads `ai_capability_route`, returns `Supplier<OcrEngine>`/`Supplier<Translator>`/`Supplier<Embedder>`/`Supplier<BatchTransport>` for a (capability, mode, kind); the suppliers re-resolve on each call with a 15 s cache so a UI change is live on the next tick.
- `PipelineStageCatalog` — the fixed list of internal stages: `ocr_page_mistral`, `translate_page`, `translate_page_upgrade`, `translate_record`, `build_searchable_pdf`, `match_persons`. Each stage is a small `@Component` implementing `ScheduledWorker { String id(); Duration interval(); void tick(); boolean enabled(); }`. Batch stages construct their `BatchOrchestrator` with `routing.batchTransport(kind)` and the generic stage; non-AI workers (`SearchablePdfWorker`, `PersonMatchWorker`) implement the same interface.
- `InternalWorkerScheduler implements SchedulingConfigurer` — 30 lines: pool size = enabled workers + 2, `registrar.addFixedDelayTask(w::tick, w.interval())` for each. It knows nothing about providers.
- `BatchOrchestrator` gains one constructor parameter, `Supplier<BatchTransport>`, and reads `provider_batch.provider_id` to pick the transport for **poll/collect of existing batches** while `submit` uses the currently routed one. That is the only orchestrator change beyond §2.2.

Enabled flags (`archiver.ocr.mistral.enabled`, `archiver.translate.batch.enabled`, `archiver.translate.record.enabled`) are replaced by "is there a route for this kind" — the compose env vars that took a night to get right (`TRANSLATE_BATCH_ENABLED`) become rows.

## 2.8 What goes wrong when swapping mid-flight, and the guards

| Hazard | Guard |
|--------|-------|
| Batches in flight at provider A when the route moves to B; A's transport no longer consulted → jobs stuck `claimed` until the 24 h timeout, then failed and re-billed at B. | `provider_batch.provider_id`; poll/collect always use the batch's own provider. A provider with `submitted` batches cannot be disabled/deleted (UI shows "draining: N batches"). |
| C3: orchestrator for kind X reconciles kind Y's `submitting` rows against the wrong provider, releases jobs Y is billing. | Fix C3 first; add `provider_id` to the reconcile query too. |
| Rate budget shared across providers (`pagesSubmittedInLastMinute(jobKind)` ignores provider). | Add `provider_id` to that query; `BatchLimits.itemsPerMinute()` per transport. |
| `job.kind` encodes the engine (`ocr_page_mistral`): moving OCR to DeepInfra leaves jobs with a lying name; `PipelineStages.OCR` lists kinds by engine; dashboards key on kind. | Increment 7: generic `ocr_page` kind with the engine chosen at claim time from the route; until then, the route table maps the existing kind to any provider and `page_text.engine` records the truth (`OcrEngine.engineId()`), which the cover sheet already prints. |
| A record half-OCR'd by engine A and half by B → mixed `content_type` (markdown vs plain) within one record. | Already handled per page (`page_text.content_type`, consumers read it). The cover sheet lists engines. Acceptable; document it. |
| Translation model with no rank row is routed → its rows rank 999 and never show, so money is spent on invisible translations. | Route save requires a rank (§2.5). |
| Credentials rotated while a batch is at the provider. | Transports read `System.getenv(credential_ref)` at call time, never cache the secret; a rotation plus redeploy is safe. |
| Switching while jobs are `submitting` (claimed locally, not yet at any provider). | Admin "switch" action closes the kind's gate, waits for zero `submitting` rows (usually < 1 tick), writes the route, reopens. Manual flow works too because `reconcile()` is provider-aware. |
| Sequential-only provider chosen for the bulk kind → 128k-page backlog through one Ollama at 4 pages/min. | UI shows `BatchLimits.itemsPerMinute()` and an ETA for the current pending count before confirming; it is a warning, not a block. |
| `page_translation.model` collision: two providers both call a model `"gpt-4o-mini"`-style names. | `Translator.modelId()` is required to be globally unique across configured providers; the registry rejects a second provider claiming the same model id. Mistral's ids stay bare to match existing rows. |

## 2.9 Testing strategy

- **Orchestrator invariants** (C1, first): `BatchOrchestratorTest` with `FakeBatchTransport` — scriptable to (a) throw after `uploadInput`, (b) throw after `createBatch` but with `findByTag` returning the id (orphan adoption, no double submit), (c) omit lines from the output (failRemaining, batch not collected until settled), (d) return an unparseable `custom_id` (whole file retried, nothing written), (e) deliver the same output twice (`isStillClaimedBy` prevents double apply), (f) exceed byte budget (overflow released with attempt restored), (g) time out (all remaining failed), (h) exhaust the per-minute budget (no submit). Assertions are on `job` and `provider_batch` rows.
- **Transport contract**: abstract `BatchTransportContractTest` with `@ParameterizedTest` over every transport; runs the same 8 scenarios against `MistralBatchTransport` (WireMock with recorded fixtures — the JSON shapes from `MistralOcrWorkerResponseTest` and the batch job/list/files responses) and `SequentialBatchTransport` (real local files, a fake sequential engine that fails every Nth call; plus a "kill the executor mid-batch and reconstruct the transport" case for resume).
- **Capability contract**: `OcrEngineContractTest`, `TranslatorContractTest`, `EmbedderContractTest` — golden bodies (byte-identical JSONL for a fixed request, which is also the Mistral faithfulness check), parse of a recorded success, of an HTTP error, of an empty body; `Embedder` dimension equals `dimensions()`; `Translator.modelId()` has a rank row.
- **Routing/registry**: seeding from properties produces today's exact routes; disabling a provider with in-flight batches is refused; unhealthy provider gates its kinds; env override wins and is reported.
- **Known-answer retrieval** (CLAUDE.md's own advice, now automated): a test fixture of three German/Czech pages and English queries with expected top-1 page, run against the configured embedder in a nightly job — the only thing that catches prefix drift.
- **Live probe** in the admin UI (`/probe`) — the manual smoke test, cheap, logged.

## 2.10 Migration plan — shippable increments, no page re-run

Each step is one PR, deployable alone, verified by the existing test suite plus the new ones named, and observable on the pipeline dashboard.

1. **Safety net.** Write `BatchOrchestratorTest` + `MistralBatchClientTest` (§2.9 a–h). Fix **C3** with a test. Commit. Nothing else changes.
2. **Extract `BatchTransport`.** `MistralBatchClient implements BatchTransport`; move `poll` field parsing and output-line parsing into it; `BatchOrchestrator` takes `BatchTransport`. Golden test proves identical bodies; deploy; watch one tick collect a batch.
3. **One client, typed config.** `ArchiverAiProperties`; single `MistralBatchTransport` bean; translation stops reading `archiver.ocr.mistral.*` (H10) with fallback aliases so the current env keeps working. Split `WorkerSchedulingConfig` into `InternalWorkerScheduler` + stage `@Component`s (§2.7) still driven by the old enabled flags. Fix **H5** (default engine) here.
4. **Capability objects.** `OcrEngine`/`Translator`/`Embedder` + Mistral implementations; `OcrBatchStage`→`OcrStage(engine)`, `TranslateBatchStage`→`TranslateStage(translator)`, `RecordTranslateBatchStage` likewise; `TranslationController` uses `Translator.translate`; `SemanticSearchController` uses `Embedder`. Behaviour identical; `PdfExportServiceTest`, `TranslationUpgradeTest`, `TranslateBatchStageTest` unchanged and green.
5. **Schema V9 + ranking table.** `ai_provider`, `ai_capability_route`, `translation_model_rank`, `provider_batch.provider_id`, `page_translation.provider_id`, `record_translation.provider_id`, the `page_best_translation`/`record_best_translation` views, seed rows reproducing today's order. `TranslationModels` reads the table; `TranslationService` reads the views. Verify: `refreshAllStale()` and `refreshAllStaleMetadata()` return **0** after deploy (proof that ranking did not move).
6. **Runtime routing + admin UI.** `ProviderRegistry`, `CapabilityRouting`, stages resolve providers per tick, admin API + `/admin/ai` page, probe, health → gate. Enabled flags removed from compose (routes replace them). Still one provider; the UI now shows it.
7. **Second provider via `SequentialBatchTransport`.** `OpenAiCompatibleProvider` (DeepInfra / Ollama): vision OCR (port of `QwenOcrWorker.callVisionApi`), chat translation, embeddings. Route `translate_page_upgrade` for **one** record to it as the first live test (the existing "Improve translation" button on one record; page_translation keeps both). Retire `QwenOcrWorker`/`GenericWorker` OCR path and the Python qwen worker.
8. **Decouple `job.kind` from engine.** New generic `ocr_page` kind; migration keeps `ocr_page_mistral` valid for history; `PipelineStages.OCR` = `[ocr_page]`; dashboards read `page_text.engine`. Only needed once a second OCR provider is actually routed.
9. **Fourth capability `COMPLETION`.** Move search-answer synthesis from `+page.server.ts` to `POST /api/search/answer`, and `PersonMatchService` rerank, behind `Completer`; remove `MISTRAL_API_KEY` and `OPENAI_API_KEY` from frontend/`archiver.openai`.

At no step is any of the 128,484 pages re-OCR'd, re-translated or re-embedded. The only re-run on the table is C2's embedding decision, which is independent of this plan and is a deliberate admin action through the (now admin-only) reset endpoint.
